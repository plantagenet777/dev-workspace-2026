# Рекомендации по внедрению LSTM и PINN в проект PdM

Документ анализирует текущий стек предиктивного обслуживания (PdM) насосной системы и даёт **подробные рекомендации** по внедрению **LSTM** (Long Short-Term Memory) и **PINN** (Physics-Informed Neural Networks) с учётом существующего пайплайна (Random Forest + правила), edge-развёртывания и ограничений по данным.

---

## 1. Текущая архитектура (краткое напоминание)

| Компонент | Реализация в проекте |
|-----------|------------------------|
| **Вход** | Телеметрия MQTT: `vib_rms`, `current`, `pressure`, `temp`; производные: `vib_crest`, `vib_kurtosis`, `cavitation_index`, `temp_delta`. |
| **Окно** | `FEATURE_WINDOW_SIZE = 30` записей на батч → один **агрегированный** вектор из 8 признаков на один запуск инференса. |
| **Сглаживание** | Усреднение последних `SMOOTHING_WINDOW_SIZE = 3` векторов признаков перед предсказанием (снижение дрожания). |
| **Модель** | Random Forest (3 класса: Healthy / Warning / Critical), StandardScaler, артефакты в joblib. |
| **Выход** | Статус (CRITICAL / WARNING / HEALTHY), сглаженный риск; слой правил (ISO 10816-3, кавитация, забивка, debris, перегрев) уточняет причину и трипы. |
| **Развёртывание** | Edge (Docker), Python 3.11, без GPU; инференс по мере накопления батча (каждые `MQTT_BATCH_SIZE` сообщений при заполненном буфере). |

**Важно:** модель по сути **не последовательностная**: на каждый запуск подаётся один 8-мерный вектор (агрегат по 30 точкам). Временная структура используется лишь частично — через скользящее среднее по 3 шагам. Это ограничивает возможность предсказывать тренды деградации и предвестники отказов.

## 2. LSTM: зачем и как внедрять

### 2.1 Что такое LSTM и почему он уместен здесь

**LSTM** — тип рекуррентной нейросети, способной запоминать долгосрочные зависимости в последовательностях. В отличие от RF, который «видит» только один срез (текущий вектор признаков), LSTM получает на вход **последовательность** таких векторов (например, последние 12 или 24 шага) и может:

- учитывать **тренд** (рост вибрации, изменение crest factor за несколько минут);
- распознавать **предотказные траектории** (медленный разгон перед Zone D, кавитацией или блокировкой);
- при необходимости выдавать **прогноз на следующий шаг** или оценку RUL (оставшийся ресурс).

**Типичные сценарии в PdM для насосов:**

- **Деградация подшипников и износа рабочего колеса:** вибрация и форма сигнала меняются постепенно; один снимок может ещё попадать в Zone B/C, тогда как последовательность уже показывает устойчивый рост.
- **Разгон перед блокировкой:** за 1–3 минуты до срабатывания вибрационной блокировки (9.0 mm/s) часто наблюдается монотонный рост; LSTM может выдать предупреждение раньше, чем порог будет достигнут.
- **Циклические режимы:** суточные или сменные изменения нагрузки; LSTM может учитывать контекст («сейчас типичный режим» vs «аномалия для этого времени»).

### 2.2 Где именно использовать LSTM (приоритеты)

| Сценарий | Описание | Приоритет |
|----------|----------|-----------|
| **Классификация по последовательности (sequence-to-one)** | Вход: последние K векторов признаков (например K=12 или 24). Выход: те же 3 класса (Healthy / Warning / Critical). Может **дополнять** или со временем заменять RF. | **Высокий** |
| **Риск/аномалия по последовательности** | LSTM-энкодер → один скаляр (риск или «расстояние до Zone D»). Объединять с текущим риском RF (например max или взвешенная сумма) для решений об алертах. | **Высокий** |
| **RUL / тренд** | Опционально: регрессия «число шагов до критического состояния» или «наклон тренда вибрации» для планирования ремонтов. | Средний |

### 2.3 Данные и форма входа для LSTM

**Источник данных:**

- Либо уже накопленная история: `telemetry_history.csv` (каждая строка — один «шаг» пайплайна с 8 признаками + timestamp, risk, status).
- Либо буфер в памяти: при каждом запуске пайплайна сохранять текущий вектор признаков (после `FeatureExtractor.get_feature_vector`) в кольцевой буфер длины K.

**Форма входа:**

- Один объект для LSTM: последовательность из T шагов по 8 признаков.
- Тензор: `(batch_size, T, 8)`. Например при batch_size=1 и T=12: `(1, 12, 8)`.
- Метки: статус на **конце** последовательности (или на шаге T+1 при предсказании «следующий шаг»). Кодирование: 0 = Healthy, 1 = Warning, 2 = Critical.

**Разметка для обучения:**

- **Синтетика:** расширить `simulate_failure.py` и/или `train_and_save.py`: генерировать длинные прогоны с известными сценариями (постепенный износ, разгон вибрации, кавитация, забивка). Для каждой последовательности последних T шагов метка = статус в конце (или через 1 шаг).
- **Реальные данные:** при наличии разметки по событиям («последние N минут до срабатывания блокировки», «нормальная работа с 14:00 до 18:00») — использовать для дообучения или валидации.

**Аугментации (по желанию):**

- Сдвиг по времени (stride), добавление небольшого шума к признакам, вырезка подпоследовательностей разной длины с приведением к фиксированному T (padding или обрезка).

### 2.4 Интеграция с текущим пайплайном

**Вариант A — параллельно с RF (рекомендуется на старте):**

- RF остаётся основным источником статуса и риска.
- Добавляется второй контур: буфер последних K векторов → LSTM → `lstm_risk` (или класс).
- Итоговый риск: например `risk = max(rf_risk, lstm_risk)` или `risk = 0.6 * rf_risk + 0.4 * lstm_risk`. Пороги (PROB_CRITICAL, PROB_WARNING) и все правила (ISO, кавитация, choked, debris, overtemp) применяются к этому итоговому риску и к статусу как раньше.
- Плюсы: откат без потери функциональности (отключить LSTM флагом), интерпретируемость сохраняется за счёт RF и правил.

**Вариант B — замена RF на LSTM:**

- LSTM единственная модель для статуса/риска; правила и пороги те же. Требует больше данных и тщательной валидации, чтобы не потерять в точности и стабильности по сравнению с RF.

**Рекомендация:** начать с **варианта A**, LSTM небольшой (1–2 слоя, 32–64 нейрона), чтобы нагрузка на edge и сложность отладки оставались приемлемыми.

### 2.5 Эскиз реализации LSTM

**Конфиг (`config/config.py` или env):**

- `LSTM_SEQUENCE_LENGTH = 12` — длина последовательности (число шагов).
- `LSTM_MODEL_PATH` — путь к артефакту (например ONNX или TorchScript).
- `USE_LSTM_RISK = true` — учитывать ли риск LSTM в итоговом риске.
- `LSTM_RISK_WEIGHT = 0.4` — вес LSTM при линейной комбинации с RF (если используется формула вида `(1-w)*rf + w*lstm`).

**Буфер последовательностей:**

- Новый модуль (например `app/sequence_buffer.py`) или расширение движка: кольцевой буфер (deque) длины `LSTM_SEQUENCE_LENGTH`, каждый элемент — вектор длины 8 (те же признаки, что и для RF). При каждом успешном вызове пайплайна добавлять текущий вектор признаков (после масштабирования тем же scaler, что и для RF). На инференс отдавать массив формы `(1, T, 8)`.

**Обучение:**

- Новый скрипт `train_lstm.py`: загрузка/генерация последовательностей, разметка по статусу в конце (или следующему шагу), обучение LSTM (PyTorch или TensorFlow). Сохранение: ONNX или TorchScript для edge; тот же StandardScaler (по 8 признакам), что и для RF, чтобы вход LSTM был в той же шкале.
- Целевая переменная: один из вариантов — (1) класс 0/1/2, (2) непрерывный риск 0…1 (тогда регрессия или второй выход). Для совместимости с текущим пайплайном удобно иметь один выход «риск» и при необходимости маппить в класс по порогам.

**Инференс:**

- При `USE_LSTM_RISK=true` и наличии артефакта: после получения RF-риска вызвать LSTM на буфере последовательности, получить `lstm_risk`, объединить с `rf_risk` по выбранной формуле, дальше как раньше (пороги, правила).

**Зависимости:**

- Добавить в проект `torch` или `tensorflow`; по желанию `onnxruntime` для лёгкого инференса ONNX на CPU. В Docker использовать образ без GPU; в документации указать минимальную версию Python (3.11) и отсутствие требования к видеокарте.

### 2.6 Риски и меры по их снижению (LSTM)

| Риск | Меры |
|------|------|
| Мало размеченных последовательностей | Активно использовать синтетику: длинные прогоны `simulate_failure.py` с разными сценариями (износ, кавитация, забивка, блокировка); аугментации (шум, сдвиг). |
| Переобучение | Небольшая сеть, dropout (0.2–0.3), early stopping по валидационной выборке; по возможности отдельный hold-out по «сценариям» (например один тип отказа не участвует в обучении, только в тесте). |
| Задержка и размер на edge | Малая LSTM (1 слой, 32–64 единицы), экспорт в ONNX; замерить время инференса на целевом устройстве; оставить возможность отключить LSTM (fallback только на RF). |
| Интерпретируемость | Не делать LSTM единственным источником решения: оставить правила и RF; LSTM рассматривать как «временной» доп. сигнал риска. |

## 3. PINN: рекомендации

### 3.1 Что такое PINN и какая «физика» уже есть в проекте

**PINN** (Physics-Informed Neural Networks) — нейросети, в функцию потерь которых добавляют слагаемые, отражающие известные физические законы или ограничения (граничные условия, ОДУ, пороги). Это улучшает обобщение при малом объёме данных и снижает предсказания, противоречащие физике.

**Уже имеющаяся в проекте физика:**

- **ISO 10816-3:** границы зон 4.5 mm/s (B/C) и 7.1 mm/s (C/D). Это не дифференциальные уравнения, а пороги; их можно ввести как **мягкие ограничения** в потери: например штраф, если при `vib_rms ≥ 7.1` модель выдаёт низкую вероятность CRITICAL.
- **Кавитация:** эвристика «высокая вибрация при низком давлении»; в коде уже есть `cavitation_index = vibration / pressure`. PINN может формализовать связь «ожидаемая вибрация в нормальном режиме vs. при кавитации» (например модель «нормальной» вибрации по давлению/току, остаток — признак кавитации).
- **Блокировка:** 9.0 mm/s — инженерный предел; в обучении можно требовать: при `vib_rms ≥ 9.0` модель обязана выдавать CRITICAL (жёстко в разметке или сильным штрафом в loss).
- **Связки процессных переменных:** температура vs. ток/давление (перегруз, забивка); при необходимости можно добавить простые балансы (например приближение dT/dt по току) для следующих итераций.

### 3.2 Где использовать PINN (приоритеты)

| Сценарий | Описание | Приоритет |
|----------|----------|-----------|
| **Потеря по зонам (zone-consistent loss)** | Если `vib_rms ≥ 7.1` — в loss поощрять высокую P(CRITICAL); если `vib_rms < 4.5` и нет других причин (кавитация, choked и т.д.) — поощрять P(HEALTHY). Уменьшает «очевидные» ошибки классификации. | **Высокий** |
| **Остаток по кавитации (cavitation residual)** | Обучить небольшую сеть: вход — давление, ток (и при необходимости температура); выход — «ожидаемая вибрация» в режиме без кавитации. На инференсе: `cavitation_residual = observed_vib_rms - predicted_vib_rms`; большой остаток → кавитация. Дополняет текущий `cavitation_index`. | **Высокий** |
| **Ограничение по блокировке** | В обучении: для примеров с `vib_rms ≥ 9.0` задать метку CRITICAL или большой штраф за не-CRITICAL. На инференсе правило «при vib_rms ≥ 9.0 → CRITICAL» уже есть в правилах; PINN выравнивает под это **саму модель**. | Средний |
| **Полноценный PINN-суррогат (ОДУ)** | Замена или дополнение блока признаков сетью, удовлетворяющей упрощённым ОДУ (например тепловая динамика, вибрация от скорости/нагрузки). Требует явных уравнений и данных. | Низкий (на будущее) |

### 3.3 Реализация по шагам

**Шаг 1 — Physics loss по зонам (только обучение):**

- В `train_and_save.py` (или отдельном `train_pinn.py`) для каждого примера вычислить дополнительное слагаемое loss:
  - Если `vib_rms >= 7.1`: добавить штраф за низкую вероятность класса CRITICAL (например отрицательный лог-правдоподобие класса 2 или квадрат (1 - P(CRITICAL))).
  - Если `vib_rms < 4.5` и по правилам нет кавитации/choked/debris/overtemp: добавить штраф за низкую P(HEALTHY).
- Итоговая потеря: `total_loss = classification_loss + lambda_zone * zone_physics_loss`. Коэффициент `lambda_zone` (например 0.1–0.3) подобрать по валидации, чтобы не ухудшить общую точность.
- То же слагаемое можно добавить при обучении LSTM: по последнему шагу последовательности проверять зону по `vib_rms` и штрафовать несоответствие выхода модели.

**Шаг 2 — Ограничение по блокировке:**

- В разметке: все примеры с `vib_rms >= VIBRATION_INTERLOCK_MMPS` (9.0) считать CRITICAL.
- Дополнительно в loss: для таких примеров сильный штраф, если модель выдаёт не CRITICAL (например cross-entropy с целевым классом 2).

**Шаг 3 — Cavitation PINN (остаток):**

- **Обучение:** отдельный скрипт `train_cavitation_pinn.py`. Данные: участки, где кавитация по правилам **не** объявлялась (нормальный режим). Входы: `pressure`, `current`, при необходимости `temp`; целевая переменная: `vib_rms`. Обучить небольшую MLP (2–3 слоя, десятки нейронов) или лёгкую 1D CNN. Сохранить модель (например ONNX) в `models/` (путь задать в конфиге, например `CAVITATION_PINN_PATH`).
- **Инференс:** в `feature_extractor` или в `predictor` после расчёта признаков вызвать эту модель: `vib_predicted = cavitation_pinn(pressure, current, temp)`; вычислить `cavitation_residual = vib_rms_observed - vib_predicted`. Передавать остаток в правила (например «если residual > порог и давление низкое → усилить кавитационный алерт») или в объединённый риск.

**Конфиг:**

- `USE_PINN_ZONE_LOSS = true`, `PINN_ZONE_LOSS_WEIGHT = 0.2` (или через env).
- `CAVITATION_PINN_PATH` — путь к артефакту кавитационного PINN; если пусто — блок кавитационного остатка не использовать.

### 3.4 Риски и меры (PINN)

| Риск | Меры |
|------|------|
| Слишком жёсткие ограничения | Выбирать вес physics loss умеренно (0.1–0.3); проверять, что accuracy/balanced_accuracy на валидации не падает. |
| Неточная или упрощённая физика | Начать с зон ISO и остатка по кавитации; не вводить сложные ОДУ без чётких уравнений и проверки на данных. |
| Доп. задержка на инференсе | Zone loss только на обучении. Cavitation PINN — один небольшой forward; замерить время и при необходимости вызывать не каждый шаг, а раз в N шагов. |

## 5. Зависимости и развёртывание

- **LSTM:** в `requirements.txt` (или отдельный файл для ML-расширений) добавить `torch` или `tensorflow`; при использовании ONNX — `onnxruntime`. В Docker — образ без GPU, явно указать в README: инференс на CPU, Python 3.11.
- **PINN:** zone loss и штраф по блокировке реализуются в скрипте обучения (NumPy/sklearn или тот же PyTorch/TF). Модель кавитационного остатка — малая сеть того же фреймворка, сохраняемая в ONNX при желании.
- **Тесты:** (1) юнит-тест буфера последовательностей (форма выхода `(1, T, 8)`); (2) проверка, что после обучения при `vib_rms >= 9.0` модель (или итоговый статус после правил) даёт CRITICAL; (3) smoke при отключённом LSTM (только RF и правила).

## 6. Краткие ссылки и литература

- **LSTM в PdM:** использование последовательностей для классификации и RUL в вибрационной диагностике (подшипники, насосы, компрессоры).
- **PINN:** Raissi et al., «Physics-informed neural networks»; в PdM чаще применяют как мягкие ограничения (пороги, остатки) rather than полные решатели PDE.
- **ISO 10816-3:** границы зон 4.5 и 7.1 mm/s (Группа 1, жёсткое крепление); в проекте реализованы в `config.config` и `app.rules`.

## 8. Целесообразность при переходе на промышленные данные и промышленную эксплуатацию

### 8.1 Когда переход на LSTM + PINN оправдан

- **Есть объём промышленных данных с разметкой по времени:** события «норма», «предупреждение», «отказ» привязаны к временным окнам. LSTM имеет смысл, когда можно обучить или дообучить его на реальных последовательностях (хотя бы сотни размеченных окон) и валидировать на других агрегатах или периодах.
- **Важны раннее предупреждение и тренды:** нужен не только текущий срез (зона по ISO), но и «разгон за последние N минут», прогноз RUL или вероятность перехода в Zone D в ближайшие часы. Тогда LSTM даёт добавленную ценность по сравнению с одним RF.
- **Кавитация и зоны плохо разделяются по одному срезу:** на реальных данных шум и наложение режимов могут давать ложные срабатывания или пропуски. PINN (остаток вибрации, zone loss при обучении) помогает привязать модель к физике и снизить противоречия с ISO и эксплуатационной практикой.
- **Готовность к поддержке ML-пайплайна:** переобучение LSTM/PINN по расписанию или при появлении новых данных, мониторинг дрейфа и версионирование артефактов. Без этого выгода от сложных моделей быстро теряется.

### 8.2 Когда разумнее остаться на RF + правила (или отложить LSTM/PINN)

- **Мало промышленных данных или нет разметки:** RF на синтетике и правила ISO уже дают понятное и объяснимое поведение. LSTM без достаточного количества реальных последовательностей склонен к переобучению или не даёт выигрыша; промышленная эксплуатация требует стабильности и предсказуемости.
- **Жёсткие требования по интерпретируемости и аудиту:** на объектах с строгим регламентом («почему сработало?») RF и правила прозрачны; LSTM и PINN добавляют «чёрный ящик» (хотя бы частично). Сначала закрепить принятие системы на RF + правила, затем рассматривать LSTM как доп. канал риска.
- **Ограничения по ресурсам на edge:** старые или маломощные контроллеры, жёсткие лимиты по памяти и времени отклика. RF + joblib лёгкие; LSTM (даже в ONNX) и дополнительный PINN увеличивают объём и латентность. Нужны замеры на целевом железе.
- **Нет команды для поддержки переобучения и валидации:** промышленная эксплуатация подразумевает периодическое обновление моделей по новым данным и реакцию на дрейф. Если этого не планируется, усложнение стека (LSTM + PINN) увеличивает риски без гарантированной отдачи.

### 8.3 Рекомендуемая стратегия для промышленного перехода

1. **Фаза 1 (ввод в эксплуатацию):** выйти на промышленные данные с **текущим стеком** (RF + правила). Собирать телеметрию и разметку (хотя бы по событиям: блокировка, кавитация, плановые остановы). Валидировать точность и приемлемость ложных срабатываний/пропусков на реальных режимах.
2. **Фаза 2 (при наличии данных):** добавить **physics loss (PINN по зонам)** в обучение RF (или простой MLP): переобучить на промышленных данных с штрафом за нарушение зон 4.5 / 7.1 и блокировки 9.0. Это минимальное изменение при максимальной совместимости с текущей логикой.
3. **Фаза 3 (по потребности):** при накоплении размеченных последовательностей и явном запросе на «раннее предупреждение» или RUL — ввести **LSTM параллельно RF** (объединение рисков, правила без изменений). Сохранить возможность отключить LSTM и работать только на RF.
4. **Фаза 4 (опционально):** cavitation PINN (остаток) и/или голова RUL у LSTM — только при доказанной пользе на промышленных данных и наличии ресурсов на поддержку.

Итог: переход на LSTM + PINN **целесообразен** при наличии промышленных данных, разметки и готовности поддерживать более сложный ML-цикл; для **первого вывода системы в промышленную эксплуатацию** предпочтительно закрепиться на RF + правила и physics loss (зоны), а LSTM вводить поэтапно после накопления данных и обоснованной потребности в временном/прогнозном сигнале.
